# Agency Operations, Lead Pipeline & PRD Status Portal

This implements the full three-portal agency app against the spec: a secret-key-protected admin panel, an auth-gated employee lead pipeline, and a public developer/PRD status view. The stack is Next.js 14 App Router, Supabase (auth-helpers), papaparse for CSV import, and Tailwind for all styling. All 36 specified source files are present, TypeScript compiles clean, and `next build` exits 0.

Watch for: **`GET /api/projects` has no authorization check** (confirmed) — it exposes all client PRD data to any unauthenticated caller. The `Converted` lead status is unreachable through the employee update flow (confirmed) — nothing in the modal or `deriveStatus()` produces it.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The admin secret-key guard is applied twice: in `middleware.ts` (edge, first line of defense) and redundantly in `app/admin/[secretKey]/page.tsx` (server component, second line). Both paths redirect to `/not-found`. The employee dashboard session check mirrors this pattern — middleware redirects unauthenticated visitors before the page ever loads, and the server component calls `supabase.auth.getUser()` as a belt-and-suspenders check.

The `PATCH /api/leads/[id]` auto-derivation chain (site visit → meeting → demo → dropped/contacted → new) correctly implements the spec priority order. The `Converted` status exists in the type system, the Badge component, and EmployeeStats analytics, but is orphaned — neither `deriveStatus()` nor the LeadUpdateModal can produce it. Leads can only reach `Converted` via direct database manipulation.

The developer portal (`/developer`) is a Server Component that reads `projects_prd` using `SUPABASE_SERVICE_ROLE_KEY`. The key never reaches the browser. The spec calls this route "public/semi-private" and the implementation delivers that correctly. However, the same data is also exposed through `GET /api/projects`, which carries no authorization check at all, making the service-role read in the Server Component the only protection that actually matters — and bypassing it via the API is trivial.

The CSV import flow requires `x-admin-key` in the request header, which `CSVImport.tsx` sends by passing `secretKey` down from the admin page server component — a reasonable pattern that keeps the secret server-originated. The same header is required on `POST/PATCH /api/projects` and `POST /api/admin/assign`. The gap is the `GET` handler on `/api/projects`.

All badge colors match spec exactly. All responsive layouts use `md:hidden` / `hidden md:block` pairs. No external UI library is imported anywhere in the component tree.

1. **Unauthenticated GET /api/projects** — `app/api/projects/route.ts` GET handler has no `isAdminAuthorized` check, exposing all client PRD records (client name, email, PRD content, blockers) to any unauthenticated HTTP request. Add `if (!isAdminAuthorized(request)) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })` at the top of the GET handler, matching the pattern already used in POST and PATCH.

2. **Converted status unreachable** — `deriveStatus()` in `app/api/leads/[id]/route.ts` never returns `"Converted"`, and `LeadUpdateModal` has no step for it. The spec lists `Converted` as a valid pipeline status. Add a "Mark as converted" checkbox or button to the employee modal (or to the admin LeadsTable actions) and handle it in the API — either as a direct status override or as the highest-priority condition in `deriveStatus`.

### Unauthenticated PRD data exposure via GET /api/projects

`app/api/projects/route.ts` defines three handlers. POST and PATCH both call `isAdminAuthorized(request)` and return 401 on failure. The GET handler does not:

```typescript
// GET /api/projects — no auth check
export async function GET() {
  const supabase = createClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.SUPABASE_SERVICE_ROLE_KEY!
  );
  const { data, error } = await supabase
    .from("projects_prd")
    .select("*, profiles!assigned_developer_id(full_name)")
    ...
```

This returns all `projects_prd` rows including `client_name`, `client_email`, `prd_content`, and `current_blocker` to any caller with no credentials. The developer portal's Server Component doesn't use this route — it directly calls Supabase with the service role — so adding auth to GET doesn't break anything in the current UI. The fix is a single `isAdminAuthorized` guard matching the POST/PATCH pattern. Confidence: **confirmed**.

### Converted status has no write path

The spec's lead status enum is: `New → Contacted → Demo Sent → Meeting Scheduled → Site Visit Requested → Converted → Dropped`. `deriveStatus()` covers all states except `Converted`:

```typescript
function deriveStatus(fields: LeadUpdateBody): LeadStatus {
  if (fields.site_visit_requested) return "Site Visit Requested";
  if (fields.meeting_scheduled)    return "Meeting Scheduled";
  if (fields.demo_website_sent)    return "Demo Sent";
  if (fields.is_interested === false) return "Dropped";
  if (fields.is_interested === true)  return "Contacted";
  return "New";
}
```

`LeadUpdateModal` has no "Mark as converted" control. `EmployeeStats` correctly filters `l.status === "Converted"` for the conversion rate, but since no code path sets that status, the metric will always show 0. Confidence: **confirmed**.

### Security posture summary

`SUPABASE_SERVICE_ROLE_KEY` is referenced only in API routes and Server Components — never in any `'use client'` file or in `lib/supabase.ts` (which uses the anon key via `createClientComponentClient`). The grep confirms zero occurrences in `components/`. The `.env.example` correctly marks it as server-side only.

Admin secret key is compared with `===` against `process.env.ADMIN_SECRET_KEY`. If `ADMIN_SECRET_KEY` is unset, both middleware and the page component treat an empty string match as a failure (middleware: `if (!adminKey || providedKey !== adminKey)` — the `!adminKey` guard covers the unset case). Confidence: **confirmed**.
