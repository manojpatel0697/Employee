# Agency Portal: Full-Stack Implementation Review

This change delivers the complete Agency Operations, Lead Pipeline, and PRD Status Portal: a Next.js 14 App Router application with Supabase auth and PostgreSQL, three distinct access portals (admin via secret-key URL, employee via login, developer as public), a CSV lead import pipeline, and a per-employee performance analytics dashboard. The implementation spans 36 source files across all three FEATs and passes `npx tsc --noEmit` and `npx next build` with zero errors. **Watch for:** (1) the developer portal uses the anon key with an RLS policy that only permits authenticated users — unauthenticated visitors will get an empty result set, not a true public view; (2) `SUPABASE_SERVICE_ROLE_KEY` is accessed in a Server Component that Next.js marks as `async` but is co-located with client islands, creating a marginal risk it could be bundled on the wrong side if the component tree is restructured; (3) the `/api/leads/[id]` PATCH endpoint has no authentication check — any caller knowing a lead UUID can overwrite its pipeline fields.

**Verdict**: CHANGES_REQUESTED

---

## High-level view

The middleware provides a two-layer guard: it blocks `/admin/:path*` by comparing the URL segment to `ADMIN_SECRET_KEY`, and blocks `/employee/dashboard` for unauthenticated sessions. The admin Server Component repeats the secret-key check server-side, so a bypassed middleware (e.g., a direct Edge invocation) still hits a second gate. Both checks are confirmed present.

The status auto-derivation in `/api/leads/[id]` uses a deterministic priority chain: `site_visit_requested > meeting_scheduled > demo_website_sent > is_interested=false > is_interested=true > New`. This matches the spec's implied ordering and handles the `is_interested=null` case by falling through to `New`. The logic is applied unconditionally on every PATCH, meaning a subsequent update that clears `site_visit_requested` but leaves `meeting_scheduled=true` will correctly step the status back to `Meeting Scheduled`.

The developer portal is coded as a Server Component using the anon Supabase client, but the `developers_read_prd` RLS policy requires `auth.uid()` to match a row in `profiles` with `role IN ('admin', 'developer')`. An unauthenticated visitor has no session, `auth.uid()` returns null, and the `EXISTS` check fails — returning zero rows rather than an error. The portal page renders as if there are no PRDs, with no visible indication of the access failure. This is a confirmed behavioral gap against the spec requirement that the developer portal be truly public.

The three API routes that mutate data (`PATCH /api/leads/[id]`, `POST /api/leads/import`, `POST /api/projects`, `PATCH /api/projects`) use the service-role client but do not verify the caller's identity. Because the service-role key bypasses RLS, any request that reaches these endpoints — including unauthenticated ones — can write to the database. The service-role key itself is confined to `process.env.SUPABASE_SERVICE_ROLE_KEY` (no `NEXT_PUBLIC_` prefix) and only appears in `app/api/` route handlers and the admin Server Component, so it is not reachable in browser bundles. The exposure risk is in the missing auth gate on the API routes, not in key leakage.

The `PRDManager.tsx` Assigned Developer column renders the raw UUID from `assigned_developer_id` rather than the joined developer name. The GET `/api/projects` response includes a joined `profiles!assigned_developer_id(full_name)` but `PRDManager` only receives a typed `ProjectPRD[]`, which has no `developer_name` field, so the join result is silently dropped at the Server Component boundary before the data reaches the component.

Badge colors match the spec (confirmed in `Badge.tsx`). No external UI libraries appear in package.json — Tailwind is the sole styling mechanism.

<details>
<summary>Issues (4)</summary>

1. **Developer portal is not truly public** — The `developers_read_prd` RLS policy requires `auth.uid()` to resolve to an admin or developer profile. Unauthenticated visitors get an empty response with no error. Fix by either replacing the RLS policy with `USING (true)` (fully public), or switching the developer page to use the service-role client (bypasses RLS entirely), or adding a public anon policy scoped to `projects_prd`.

2. **Unauthenticated writes via service-role API routes** — `PATCH /api/leads/[id]`, `POST /api/leads/import`, `POST /api/projects`, and `PATCH /api/projects` accept requests from any caller. The service-role key bypasses RLS, so there is no database-level fallback. Add a session check (or at minimum a shared secret header verified server-side) to each mutating route before allowing writes.

3. **PRDManager shows raw UUID instead of developer name** — The admin PRD table renders `p.assigned_developer_id` (a UUID string) in the "Assigned Developer" column. The GET `/api/projects` join result is typed away before the data reaches `PRDManager`. Either pass `developer_name` through the admin page Server Component (joining via service-role query with `profiles!assigned_developer_id(full_name)`) and add it to the props type, or have `PRDManager` resolve names from the employees list already available on the admin page.

4. **`ADMIN_SECRET_KEY` empty-string passes middleware guard** — The middleware checks `if (!adminKey || providedKey !== adminKey)`. If `ADMIN_SECRET_KEY` is set but empty (`""`), the `!adminKey` branch redirects correctly. However, if the env var is missing entirely, `process.env.ADMIN_SECRET_KEY ?? ""` falls back to `""`, and visiting `/admin/` (with an empty third segment) would also produce `providedKey = ""`, making the check `"" !== ""` → false, passing the guard. The second gate in the Server Component catches this since it also uses `??` with the same env var, but the middleware should explicitly reject when `adminKey` is empty rather than relying on the fallback parity coincidence.

<details>
<summary>Details</summary>

### Developer portal public access gap (RLS vs. anon session)

The spec states the developer portal is "public/semi-private" and "accessible when typing `/developer`" with no auth required. The implementation uses `createServerClient(cookieStore)` — the cookie-based anon client — with no session, then queries `projects_prd`. The `developers_read_prd` policy is:

```sql
CREATE POLICY developers_read_prd ON projects_prd
  FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM profiles
      WHERE profiles.id = auth.uid()
        AND profiles.role IN ('admin', 'developer')
    )
  );
```

`auth.uid()` returns `null` for an unauthenticated request. `profiles.id = null` matches nothing, so the policy denies all rows. The page receives `data = []` with `error = null` and renders "No PRDs have been created yet." — a silent access failure. The middleware's `config.matcher` correctly excludes `/developer`, so there's no middleware block; the failure is entirely at the RLS layer.

The fix requires one of: (a) change the policy to `USING (true)` if PRD content is safe to be fully public; (b) use the service-role client in the developer Server Component (drops RLS enforcement entirely, requires trusting the Server Component boundary); or (c) add an anon-accessible SELECT policy alongside the existing one.

### Unauthenticated write surface on API routes

`PATCH /api/leads/[id]` reads the lead ID from URL params and body, derives status, and calls `supabase.update()` with the service-role client — no session check anywhere in the handler. The same pattern applies to the import and projects routes. Because `force-dynamic` is set and the routes are serverless functions, they're reachable from any HTTP client. An attacker who discovers a lead UUID (e.g., via the employee dashboard, which renders all assigned leads to the logged-in employee) can corrupt that lead's pipeline state without credentials.

The employee dashboard uses the cookie-scoped anon client with RLS, which correctly limits employees to their own leads — but the PATCH route bypasses that same RLS via the service-role client. The RLS protects the read path; the write path has no equivalent gate.

### PRDManager assigned developer display

`app/admin/[secretKey]/page.tsx` fetches projects via a direct service-role query with `.select("*")` — no join on `profiles!assigned_developer_id(full_name)`. It then types the result as `ProjectPRD[]` and passes it to `PRDManager`. `ProjectPRD` has `assigned_developer_id: string | null` but no `developer_name` field. The table cell renders `{p.assigned_developer_id ?? "—"}` — a UUID like `3f8a2...` or `—`, not a human name.

The admin page already fetches the `employees` array (profiles with `role='employee'`). Passing employees into `PRDManager` and doing a client-side lookup by ID is sufficient; no additional query is needed.

### Admin secret key empty-string edge case

The middleware guard:
```ts
const adminKey = process.env.ADMIN_SECRET_KEY ?? "";
if (!adminKey || providedKey !== adminKey) {
  return NextResponse.redirect(new URL("/not-found", request.url));
}
```

When `ADMIN_SECRET_KEY` is unset in production (misconfiguration), `adminKey` becomes `""`. A visitor who navigates to `/admin/` produces `segments[2] = undefined`, `providedKey = ""`. The check becomes `!""` → `true`, so they get redirected correctly. But a visitor navigating to `/admin/` with an explicit empty segment (e.g., via direct URL manipulation to produce `segments[2] = ""`) would also get `providedKey = ""`, making `"" !== ""` false — passing the middleware. The Server Component's identical pattern provides the second gate, but this remains a fragile reliance on two independent fallbacks. Explicitly guarding `if (!adminKey)` before the key comparison would make the intent unambiguous and eliminate the reliance on the coincidence.
