# Agency Operations, Lead Pipeline & PRD Status Portal — Full Implementation Review

This change implements a three-portal Next.js 14 App Router application from scratch: an admin panel behind a secret key route, an employee portal protected by Supabase session auth, and a public developer PRD status page. The implementation covers all 36 specified files across scaffold, database schema, API routes, and UI components. The approach is server-component-first with client islands where interactivity is required; the service-role key is used exclusively in server-side code and API routes.

**Watch for:** (1) **confirmed** — `/api/leads` GET route has no auth guard; any caller can retrieve all leads. (2) **confirmed** — `/developer` page uses the service-role key to bypass the `developers_read_prd` RLS policy, making the page publicly readable but rendering the RLS policy that governs this table entirely ineffective. (3) **confirmed** — the `employees_own_leads` RLS policy is scoped `FOR ALL` instead of `SELECT + UPDATE`; employees with a raw DB connection could INSERT or DELETE leads. (4) **confirmed** — the admin tables (leads, profiles) have no write-guard in the RLS for the service-role routes other than the `x-admin-key` header check, which is an application-layer guard only.

**Verdict**: NEEDS_CHANGES

---

## High-level view

All three portals are present and structurally complete. The admin panel applies a double guard (middleware + page server component both check `ADMIN_SECRET_KEY`), the employee dashboard is protected by both the middleware session check and a server-side `auth.getUser()` call, and the developer portal requires no credentials. File count matches the spec: 36 files committed across scaffold, migrations, API routes, and components.

The `deriveStatus` logic in `/api/leads/[id]/route.ts` faithfully implements the spec's priority chain (site_visit > meeting > demo > not-interested > interested > new). The PATCH route additionally gates on a valid Supabase session, preventing anonymous updates. The CSV import route correctly uses papaparse with `{ header: true, skipEmptyLines: true }`, maps to the full `Lead` insert shape, and returns `{ inserted: count }`.

The developer portal bypasses the `developers_read_prd` RLS policy by using the service-role client directly. The comment acknowledges this, but the consequence is that all PRD data — including client emails and blocker notes — is public to any internet visitor, not just authenticated developers. The spec says the portal is "public/semi-private" which is ambiguous, but the RLS policy exists precisely to restrict to developer/admin roles. These two decisions are in direct conflict with each other. If the intent is a fully public view, the policy should be dropped. If the intent is developer-role-only, the service-role client should not be used here.

The `employees_own_leads` RLS policy uses `FOR ALL` rather than the spec's "can only SELECT and UPDATE". This grants INSERT and DELETE permissions to employees at the database level, contradicting the spec's intent. In practice the application never sends INSERT/DELETE via the user auth client, but the policy boundary is broader than specified.

`GET /api/leads` has no authentication or authorization check. Any unauthenticated HTTP client can call this endpoint and retrieve the full leads table — all company names, contact emails, phone numbers, and pipeline notes — without a session or admin key. All other write routes on leads and projects are properly guarded.

Badge colors are exactly as specified: `New=gray-100/gray-700`, `Contacted=blue-100/blue-700`, `Demo Sent=purple-100/purple-700`, `Meeting Scheduled=yellow-100/yellow-700`, `Site Visit Requested=orange-100/orange-700`, `Converted=green-100/green-700`, `Dropped=red-100/red-700`. The service-role key appears only in API routes and Server Components — never in a `'use client'` file. No external UI libraries are imported; all styling is Tailwind.

<summary>Issues (4)</summary>

1. **Unauthenticated GET /api/leads** — `GET /api/leads` has no session or admin-key check. Add an `isAdminAuthorized` header check (matching the pattern used in the other admin API routes) or require a valid session before returning lead data.

2. **Developer portal bypasses RLS with service-role key** — `app/developer/page.tsx` uses `SUPABASE_SERVICE_ROLE_KEY`, bypassing the `developers_read_prd` policy entirely and exposing all PRD data (client emails, blocker notes) to unauthenticated visitors. Either use the anon key and require developer login, or remove the `developers_read_prd` policy if the intent is a fully public page — the current state has both a policy that implies restricted access and an implementation that ignores it.

3. **RLS policy FOR ALL instead of SELECT + UPDATE on leads** — `employees_own_leads` is `FOR ALL`, granting employees INSERT and DELETE at the DB level. Change to two separate policies: `FOR SELECT USING (...)` and `FOR UPDATE USING (...) WITH CHECK (...)` to match the spec.

4. **Mobile responsiveness incomplete on dense tables** — `LeadsTable`, `EmployeeStats`, and `PRDManager` render full-width tables with `overflow-x-auto` but no column hiding or card-based fallback below `sm:` breakpoint. The portal pages themselves are max-width constrained but these wide tables will scroll horizontally on narrow viewports. This meets a minimum bar but is below the "mobile-responsive layout" criterion.

<summary>Details</summary>

### Unguarded GET /api/leads exposes full lead data

`GET /api/leads` uses the service-role client and returns all leads joined with assigned profiles — company name, contact person, phone, email, source, pipeline state, and notes — with no check at all. Every other route that touches sensitive data checks either `isAdminAuthorized(request)` (for admin routes) or the Supabase session (for the leads PATCH). This route was not covered by either pattern.

```
GET /api/leads
→ no session check
→ no x-admin-key check
→ returns full leads table to any caller
```

The fix is a single `isAdminAuthorized` guard at the top of the GET handler, consistent with how the assign, import, and projects routes protect their writes.

### Developer portal: service-role key conflicts with RLS intent

The `developers_read_prd` policy in the migration requires the caller to be an authenticated user with role `admin` or `developer`. The developer portal page uses `createClient(URL, SERVICE_ROLE_KEY)` which bypasses all RLS and returns every row. The comment in the file acknowledges this but presents it as a deliberate workaround ("the anon client would return an empty result set for public visitors").

The result is that the migration defines access controls for this table that the application never enforces. A visitor to `/developer` without any account can read all PRDs including `client_email` and `current_blocker`. If the design intent is "public read", the migration should be updated to drop the policy and instead define a public anon-readable table (or use `FOR SELECT USING (true)`). If the intent is developer-only, the portal should require login and use the user's own session client.

### RLS over-permission on leads

```sql
-- current
CREATE POLICY employees_own_leads ON leads
  FOR ALL
  USING (assigned_to = auth.uid() OR ...)
  WITH CHECK (assigned_to = auth.uid() OR ...);
```

`FOR ALL` covers SELECT, INSERT, UPDATE, and DELETE. The spec states: "Employees can only SELECT and UPDATE leads where assigned_to = auth.uid()." The appropriate correction is two separate policies (`FOR SELECT` and `FOR UPDATE`) so employees cannot bypass application logic to insert or delete rows.

### Mobile responsiveness: tables lack small-screen handling

The three admin tables (`LeadsTable`, `EmployeeStats`, `PRDManager`) each have 7–10 columns and use `overflow-x-auto` for horizontal scroll. The employee `LeadsList` is similar. `overflow-x-auto` is the minimum viable approach, but the spec requires a "mobile-responsive layout." On a 375px viewport these tables require horizontal scrolling through 8+ columns, which is difficult to use. A card-based fallback below `md:` breakpoint (using CSS `hidden md:table-cell` on non-critical columns) would satisfy the spec; the current implementation technically scrolls but is not ergonomic.
